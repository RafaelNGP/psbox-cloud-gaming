## image

gpu.cpp is shared by PS5, Linux and Windows. PS4 uses its own path. Decoded NV12 (HW) or I420 (SW) planes are copied into R8/R8G8 images (gpu.cpp:849-852, 1250-1261). One compute pass then does four things: bilinear chroma with type-0 siting hardcoded (nv122rgb.comp:24-27, yuv2rgb.comp:31-34), a libplacebo-style deband with a per-frame random seed and grain forced to 0 since v1.6.9 (gpu.cpp:1230-1231, 1273-1274; nv122rgb.comp:45-57), and the BT.709 limited-to-full matrix (nv122rgb.comp:58-61). The result is stored in an **RGBA8** image (gpu.cpp:853).

Default look:
- **Upscaler 2:** FSR plus the Anime4K Restore-CNN-S in place (settings.h:27, stream_screen.cpp:36-38, gpu.cpp:888-895, a4k_r_conv3.comp:56-63).
- **Sharpness 2:** RCAS at 0.5 stops with denoise (stream_screen.cpp:32, gpu.cpp:1099-1105, rcas.comp:21).
- **Deband auto:** in practice always 'low' at 4 Mbps or more (auto_deband.cpp:7-12). The header still says 'off above ~10' (auto_deband.h:9-10).

The swapchain is fixed at 3840x2160 B8G8R8A8 SDR by the videoout WSI (PS5_Mesa wsi_common_videoout.c:55-56, 389, 720-723; log line 'gpu: display 3840x2160'). So our EASU always does an exact 2x upscale from 1080p into an **8-bit** image (gpu.cpp:789, 1082-1093), and RCAS plus the overlay then write the swapchain (rcas.comp:40-49). Scaling in gamma space is what FSR requires, so it is correct (ffx_fsr1.h:86-95).

The picture is quantised to 8 bits three times and dithered nowhere. The limited-to-full expansion alone leaves 36 of 256 grey codes unreachable (verified numerically).

Tooling:
- now.ppm is a 960x540 CPU conversion that keeps every second pixel (stream_player.cpp:1211-1225).
- screen.ppm is the 4K readback.
- imgtest varies only upscaler and sharpness, with a fixed 1280x720 crop (stream_player.cpp:1248-1266).
- drawMs is CPU time (stream_player.cpp:966), so GPU cost is not measured.

## network

Receive: libjuice UDP, 1 MiB SO_RCVBUF (libjuice/src/udp.c:81-84) → DTLS queue → pool thread. SRTP is unprotected inside the mbedtls ReadCallback under mSslMutex (libdatachannel/src/impl/dtlstransport.cpp:649-660; replay window 1024, dtlssrtptransport.cpp:344). Chain: RtcpReporter, then H264Receiver (mediahandler.cpp:66-71; stream_session.cpp:548-561). Offer: H.264 with nack, nack pli and goog-remb only (stream_session.cpp:535-544; description.cpp:1251-1254). There is no RTX, RED/ULPFEC or transport-cc. The server retransmits on the same SSRC (h264_receiver.h:9-10).
H264Receiver: a gap gets an immediate NACK (h264_receiver.cpp:154-166,371) and a re-NACK every RTT+10 ms, at most 5 (168-177,422-427). A frame goes out the moment its marker arrives with no hole (257-315). So without loss the transport adds almost nothing: first packet→complete ≈2.1-2.3 ms is the server/link spread (HANDOFF_HW_DECODING.md:222-223). A hole blocks every later frame for up to lossWait = 2·RTT+30 ms (floor 40-55 ms when RTT<30, else 90; max 300; 415-420). RTT is the SCTP srtt (stream_session.cpp:924-931). When the wait runs out, the frame is dropped, and so is every frame after it until a key frame (NAL 5 or SPS, line 34). resync() accepts that key frame only if the packet before it is present (217-255). Key frame requests go out as PLI plus a data-channel request (144-152; stream_session.cpp:708-722), repeated every 300 ms (399). The player has its own separate 500 ms limiter (stream_player.cpp:1301-1311). REMB reacts only to loss above 10% (rtcp_reporter.cpp:211-224). Stats are counters and per-second maxima (video_stats.h:134-149), with no recovery-delay, freeze-length or late-retransmission metrics. The test hook loss=N always redelivers 30 ms after the NACK (h264_receiver.cpp:124-130).

## pacing

On the PS5 the video thread does decode, skip decision and draw itself (no async present: caps() in display_ps5.cpp:532-538). After decode: the 'behind' rule (stream_player.cpp:893-902) looks only at the network queue: at 120 Hz it skips when more than 2 frames wait, or when 1 waits and this frame is over 35 ms old; at 60 Hz it skips when more than 1 waits. Then the fps limit, drawPic(no wait, then wait) (930-937) and present (938).

gpu::beginFrame waits for the previous frame's fence (gpu.cpp:957-966). The vkWaitForPresentKHR 50 ms branch is OFF by default: g_noPresentWait=true (gpu.cpp:181, since bf77b09), so it only polls. Then acquire (995). present() submits one command buffer plus a present with an id (1292-1334). The RADV videoout WSI is FIFO only (wsi_common_videoout.c:924), forces at least 3 images (:1204, so swap=2 does nothing), and a thread flips with VSYNC after WaitForFences (:569-600).

On screen p50 minus decode p50 minus draw is about 2.2 ms with both HW and SW (app-run7 zc: 8.09-5.71-0.20; sw: 7.63-5.05-0.40), which looks like that 2 ms tick plus a GPU pass shorter than 2 ms.
